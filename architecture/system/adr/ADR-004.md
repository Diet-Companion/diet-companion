context:
  text: One Owner uses the app. The backend is reachable from the internet (ADR-001 a), so something must limit access to
    the Owner. IF-001 1.0.0 carries a placeholder API-key header (ADR-001 assumption A-002). The Owner first chose passkeys,
    then postponed them and chose a simple login with a password and a session. No custom domain is planned, so a stable passkey
    domain is not available yet.
  cites:
  - ADR-001
  - Diet-Companion/diet-companion#37
  - Diet-Companion/diet-companion#37 comment 7126210508
  - Diet-Companion/diet-companion#37 comment 7126659305
options:
- key: a
  summary: Passkey (WebAuthn) login. Only the Owner's registered passkey signs in; the backend issues a signed session cookie.
    No password and no shared key.
  satisfies:
  - REQ-003
  - REQ-007
  pros: No secret to type or leak; phishing-resistant; nothing secret in the client bundle.
  cons: Needs a stable domain, because passkeys are bound to it, and an enrollment and recovery path. Postponed by the Owner.
  cost: A WebAuthn library and an enrollment flow; effort is not stated by any source (A-006).
  reversibility: two-way
  risks: Changing the domain later invalidates registered passkeys. Losing every passkey without a recovery path locks the
    Owner out.
  constraints:
  - id: ADR-004/C-001
    statement: A passkey can be registered only from an existing Owner session or through a one-time enrollment path decided
      in a later ADR. There is no open sign-up.
    kind: interface
    check: review
  - id: ADR-004/C-002
    statement: The backend stores only WebAuthn public credential data for the Owner's passkeys, in the ADR-003 database.
      It stores no private key or shared secret.
    kind: data
    check: review
  affects:
  - CMP-001
  - CMP-002
  - IF-001
  consequences: IF-001 would gain passkey registration and sign-in operations. CMP-002 would own credential data.
  cites:
  - ADR-001
  - ADR-003
  - Diet-Companion/diet-companion#37 comment 7126210508
  - A-006
- key: b
  summary: Keep a shared API key sent in a header by the client.
  satisfies:
  - REQ-003
  pros: Simplest to build; already in the IF-001 placeholder.
  cons: The key sits in the client bundle or on the phone and cannot be rotated without a release. The Owner rejected a shared
    API key.
  cost: Lowest build effort; not stated by any source (A-006).
  reversibility: two-way
  risks: Anyone who extracts the key has full access to the Owner's data and the paid recognition API.
  constraints:
  - id: ADR-004/C-003
    statement: The key is held in hosting secrets and compared in constant time; it is rotated on any suspected exposure.
    kind: technology
    check: review
  affects:
  - CMP-001
  - CMP-002
  consequences: No sign-in screen; weakest protection.
  cites:
  - ADR-001
  - Diet-Companion/diet-companion#37 comment 7126210508
- key: c
  summary: Delegate sign-in to an external identity provider (OIDC) and allow only the Owner's account.
  satisfies:
  - REQ-003
  - REQ-007
  pros: No credential storage in our backend.
  cons: A new runtime dependency and an account to manage. It adds third-party availability to every sign-in.
  cost: Provider tier and fees are not stated by any source (A-006).
  reversibility: two-way
  risks: A provider outage or policy change locks the Owner out.
  constraints:
  - id: ADR-004/C-004
    statement: The backend accepts only the one configured account identifier from the identity provider.
    kind: interface
    check: review
  affects:
  - CMP-001
  - CMP-002
  consequences: CMP-002 gains an external dependency that needs its own test seam.
  cites:
  - ADR-001
  - A-006
- key: d
  summary: Password login with a server-side session. One Owner password, checked by the backend over HTTPS; success issues
    an opaque session cookie (HttpOnly, Secure, SameSite=Strict) that refers to a session row. No sign-up and no shared API
    key.
  satisfies:
  - REQ-003
  - REQ-007
  - Diet-Companion/diet-companion#37 comment 7126659305
  pros: Simple to build and to test; needs no custom domain; the client holds no secret; a session can be revoked on logout;
    the Owner can move to passkeys later.
  cons: A password can be guessed, phished or reused, so it is weaker than passkeys. Needs login throttling. The Owner must
    manage the password.
  cost: Build effort is not stated by any source (A-006); no library or domain fee is known.
  reversibility: two-way
  risks: Weak password or missing throttling exposes the Owner's data and the paid recognition API. Recovery means setting
    a new hash in hosting configuration.
  constraints:
  - id: ADR-004/C-005
    statement: Every IF-001 operation except getReadiness and loginOwner requires a valid Owner session; otherwise it returns
      401 auth.required.
    kind: interface
    check: review
  - id: ADR-004/C-006
    statement: Only a salted hash of the Owner password made with a memory-hard algorithm (argon2id or scrypt) exists, held
      in hosting secret configuration. No plain password is stored, logged or put in the repository or client.
    kind: technology
    check: review
  - id: ADR-004/C-007
    statement: Sessions are stored in the ADR-003 database with an expiry and removed on logout, never in process memory,
      so ADR-001/C-002 holds. The cookie carries only an opaque random id.
    kind: deployment
    check: review
  - id: ADR-004/C-008
    statement: Failed logins are throttled and answered with the same auth.failed error whatever the cause. There is no sign-up
      and no password-reset path other than setting a new hash in hosting configuration.
    kind: interface
    check: review
  affects:
  - CMP-001
  - CMP-002
  - IF-001
  consequences: IF-001 gains loginOwner and logout and a session security scheme. CMP-002 owns session rows. CMP-001 gets
    a sign-in screen.
  cites:
  - ADR-001
  - ADR-003
  - Diet-Companion/diet-companion#37 comment 7126659305
recommended:
  option: d
  reason: It is the Owner's latest stated choice (comment 7126659305). It needs no custom domain, keeps the client free of
    secrets and fits the single-Owner scope. Passkeys (option a) remain a later step.
