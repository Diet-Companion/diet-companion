title: How label photos are turned into product values

context:
  text: REQ-003 needs name, shop, calories, protein and fat read from a label photo and saved without confirmation, asking
    only for what is missing (AC-002, AC-003, AC-004, AC-007, AC-008). The photo must be deleted after save or refusal (AC-005,
    AC-011 to AC-013). Typical add time is about 5 minutes (REQ-007). No source states recognition accuracy or latency (A-003).
  cites:
  - REQ-003
  - REQ-007
  - A-003
options:
- key: a
  summary: Send the photo from the backend to a hosted multimodal model API through an adapter (CMP-003), asking for structured
    values with null for anything not found.
  satisfies:
  - REQ-003
  - REQ-007
  pros: Handles varied label layouts and returns structured fields; no parser to maintain.
  cons: The photo leaves our system to a third party; the output can be wrong with no confirmation step; there is a per-call
    cost.
  cost: Per-call price and volume are not stated by any source; open assumption A-001.
  reversibility: two-way
  risks: A misread value is saved without review, because REQ-003 excludes confirmation. The provider's photo retention could
    conflict with the deletion ACs.
  constraints:
  - id: ADR-002/C-001
    statement: The label photo is held only in memory for the request; it is never written to durable storage or logs, and
      is not kept after the response.
    kind: data
    check: review
  - id: ADR-002/C-002
    statement: Only CMP-003 may call a recognition provider; the provider is replaceable by a fake at a process boundary.
    kind: dependency
    check: review
  - id: ADR-002/C-003
    statement: The provider is used only on terms that do not retain or train on submitted photos.
    kind: other
    check: review
  affects:
  - CMP-002
  - CMP-003
  consequences: A provider account and secret must be managed in hosting; recognition quality becomes an operational concern.
  cites:
  - REQ-003
  - A-001
  - A-003
- key: b
  summary: Use a hosted OCR service for text and our own parser for the label panel.
  satisfies:
  - REQ-003
  pros: Deterministic parsing that can be tested with fixtures.
  cons: Layouts and languages vary; the parser takes sustained effort and fails on unusual panels.
  cost: Not stated; open assumption A-001.
  reversibility: two-way
  risks: More asks for missing values than option a, so the add flow is slower.
  constraints:
  - id: ADR-002/C-004
    statement: The photo is held only in memory for the request and never persisted or logged.
    kind: data
    check: review
  - id: ADR-002/C-005
    statement: Only CMP-003 calls the OCR service.
    kind: dependency
    check: review
  affects:
  - CMP-002
  - CMP-003
  consequences: Parser code and its fixtures are part of CMP-003.
  cites:
  - REQ-003
  - A-003
- key: c
  summary: Recognise on the device in the client and send only the values to the backend.
  satisfies:
  - REQ-003
  pros: The photo never leaves the phone.
  cons: Needs a model or OCR library inside the client; accuracy depends on the device; it is heavy for a web client.
  cost: Effort is not stated; open assumption A-003.
  reversibility: costly
  risks: Recognition logic lives in the client, so changes need a new client release.
  constraints:
  - id: ADR-002/C-006
    statement: The client submits recognised values through IF-001 createProduct; the backend still enforces R-002 and R-003.
    kind: interface
    check: review
  affects:
  - CMP-001
  - CMP-002
  consequences: CMP-003 would not exist; IF-001 addProductFromLabelPhoto would be dropped.
  cites:
  - REQ-003
  - A-003
recommended:
  option: a
  reason: It reads varied labels into structured fields with the least code, and the deletion rule is met by never storing
    the photo (C-001). Accuracy is unmeasured (A-003), so the adapter seam keeps the choice two-way.
