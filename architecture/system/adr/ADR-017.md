context:
  text: 'REQ-013 and REQ-014 need a day plan and a meal log with the same entry forms: a product with whole grams or whole
    pieces, or a whole dish (R-007). Confirming a meal copies its plan entries into the log and the plan stays unchanged (REQ-014/AC-001,
    AC-002). Both are per day and per meal and later feed day and meal totals (REQ-010, REQ-015). No table exists for them
    (migrations 001 to 006). Migrations are forward-only and run with the previous revision serving (ADR-008/C-001, C-002);
    only CMP-002 reaches the database (ADR-003/C-002); a record keeps the exact product or dish id (R-009, ADR-012/C-005,
    ADR-014).'
  cites:
  - REQ-013
  - REQ-014/AC-001
  - REQ-014/AC-002
  - R-007
  - R-009
  - ADR-008/C-002
  - ADR-012/C-005
  - backend/migrations/005_create_dishes.sql
options:
- key: a
  summary: One table day_entries with a kind column (plan or log). Plan and log rows have the same columns. Confirming a meal
    inserts log rows copied from the plan rows of that day and meal.
  satisfies:
  - REQ-013/AC-001
  - REQ-014/AC-001
  - REQ-014/AC-002
  - REQ-014/AC-008
  - ADR-008/C-002
  pros: One shape, one read path and one guard. Confirm is one insert-select. One totals function serves plan and log (ADR-019).
    Adds new tables only, so the previous revision keeps working.
  cons: A wrong kind in a query mixes plan and log rows. Plan and log cannot have different retention or indexes without a
    split.
  cost: One migration and one store module in CMP-002. Build effort not stated (A-034).
  reversibility: costly
  risks: A missing kind filter would count plan entries as eaten. Mitigated by one store function that always takes kind,
    a check constraint on kind, and integration tests on real PostgreSQL (ADR-008/C-004).
  constraints:
  - id: ADR-017/C-001
    statement: 'Migration 007 is forward-only and adds only new tables. day_entries: id text primary key; kind text not null
      check in (plan, log); day date not null; meal text not null check in (breakfast, brunch, lunch, afternoon_snack, dinner);
      position integer not null check >= 0; product_id text null references products(id); dish_id text null references dishes(id);
      grams integer null check > 0; pieces integer null check > 0; from_dish_id text null references dishes(id); created_at
      timestamptz not null. Checks: exactly one of product_id and dish_id; a product row has exactly one of grams and pieces;
      a dish row has neither; from_dish_id only on a product row. Unique (kind, day, meal, position). Index on (kind, day).'
    kind: data
    check: review
  - id: ADR-017/C-002
    statement: Entry ids are generated by CMP-002, never reused. The only update after insert is grams or pieces of a product
      row (changeLogEntry, changePlanEntry). product_id, dish_id, from_dish_id, kind, day and meal are never rewritten. Removing
      an entry deletes its row. A new entry takes the next position in its day and meal.
    kind: data
    check: review
  - id: ADR-017/C-003
    statement: A new entry may reference only a selectable product or dish (entry.invalid, reasons product_not_selectable,
      product_not_found, dish_not_selectable, dish_not_found). An existing entry keeps its exact id for life, even when the
      product or dish is later replaced or soft-deleted; its amount can still be changed. Every response returns the product
      or dish by the exact id, in any state, with replaced_by, deleted and selectable (ADR-014/C-002). Pieces need a piece
      weight on that exact product id (R-007).
    kind: interface
    check: review
  - id: ADR-017/C-004
    statement: 'Every mutating handler calls one guard function in CMP-002, in the same transaction as the write, in this
      order: today from ADR-016''s function; the day window of the kind (plan: today and the next day; log: not after today,
      A-035); the day is open (ADR-019); then the entry checks. No handler takes today from a request (ADR-016/C-001).'
    kind: interface
    check: review
  - id: ADR-017/C-005
    statement: 'confirmMealAsPlanned runs in one transaction: it inserts log rows with new ids and the same product_id, dish_id,
      grams, pieces and meal, in plan order, from the plan rows of the same day and meal, and never writes to plan rows. It
      refuses a meal without plan rows (plan.meal_empty) and a meal that already has log rows (log.meal_not_empty, A-037).'
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: IF-001 1.5.0 exposes plan and log through separate operations over one table. Totals read one table with a
    kind filter.
  cites:
  - REQ-014/AC-001
  - REQ-014/AC-002
  - ADR-008/C-002
  - A-034
- key: b
  summary: 'Two tables with the same columns: plan_entries and log_entries. Confirming a meal inserts log_entries rows copied
    from plan_entries.'
  satisfies:
  - REQ-013/AC-001
  - REQ-014/AC-001
  - REQ-014/AC-002
  - ADR-008/C-002
  pros: A query on one table cannot mix plan and log. Each table can get its own indexes later. The log table is the one REQ-015
    reads for what was eaten.
  cons: Two identical tables, two store paths and a totals function that takes a table. A change in the entry shape is made
    twice.
  cost: One migration with two tables and slightly more store code than a. Build effort not stated (A-034).
  reversibility: costly
  risks: The two shapes drift apart over time. Mitigated by one shared column definition in the migration and a test that
    compares them.
  constraints:
  - id: ADR-017/C-006
    statement: Migration 007 is forward-only and adds only plan_entries and log_entries with the columns, checks and unique
      key of ADR-017/C-001, without the kind column and with unique (day, meal, position) in each.
    kind: data
    check: review
  - id: ADR-017/C-007
    statement: ADR-017/C-002, C-003 and C-004 hold for both tables. One shared store function builds both, so the entry rules
      exist once.
    kind: data
    check: review
  - id: ADR-017/C-008
    statement: confirmMealAsPlanned is one transaction that inserts into log_entries from plan_entries and never writes to
      plan_entries (ADR-017/C-005 otherwise unchanged).
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: Same interface as a. The database holds two tables for one concept.
  cites:
  - REQ-014/AC-002
  - ADR-008/C-002
  - A-034
- key: c
  summary: One table day_entries where a log row may carry plan_entry_id pointing at the plan row it was confirmed from.
  satisfies:
  - REQ-014/AC-001
  - REQ-014/AC-002
  pros: A later comparison could match a log row to its plan row. Confirm keeps the link.
  cons: 'No source asks for the link: REQ-015 is a draft and compares meals, not rows. A plan row removed after confirming
    needs a rule for the link. The link couples the log to the plan, against the independence AC-002 describes.'
  cost: Migration plus link rules and tests. Build effort not stated (A-034).
  reversibility: costly
  risks: Dangling or stale links when the plan changes after a confirm.
  constraints:
  - id: ADR-017/C-009
    statement: day_entries has plan_entry_id text null references day_entries(id), set only on log rows made by confirmMealAsPlanned,
      and on delete of the plan row it is set to null.
    kind: data
    check: review
  - id: ADR-017/C-010
    statement: ADR-017/C-001 to C-005 hold, and no total or result reads plan_entry_id.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: A plan row removal also updates log rows, which touches log rows of a day that may later be closed.
  cites:
  - REQ-014/AC-002
  - A-034
recommended:
  option: a
  reason: The plan and log entries have one shape, and confirming is one copy. One table keeps one guard and one totals function
    (REQ-013, REQ-014). Option b doubles code for no stated need. Option c adds a link no requirement asks for.
