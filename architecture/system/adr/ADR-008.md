context:
  text: The catalog lives in Cloud SQL for PostgreSQL, reached only by CMP-002 (ADR-003 b, ADR-003/C-002), with name-plus-shop
    uniqueness enforced by a database constraint on normalised values (R-003) and required values by R-002. Session rows live
    in the same database (ADR-004/C-007). IF-001 1.0.0 is an approved OpenAPI spec (architecture/system/interfaces/IF-001/openapi.json);
    specs are approved before code (S-ARCH-021) and conformance compares the implemented interface with the declared version
    (S-ARCH-026). Cloud Run instances are stateless and may run in parallel during a deploy (ADR-001/C-002). The choice is
    written in terms that hold for any ADR-007 option; named libraries come after that decision.

options:
- key: a
  summary: Spec-first with hand-written SQL migrations. The OpenAPI file stays the source of truth; request and response types
    and validators are generated from it, and a generated implemented-interface report is compared with the approved version.
    The schema is changed only by ordered, forward-only SQL migration files with a small migration runner and a typed query
    layer (no full ORM).
  satisfies:
  - REQ-003
  - REQ-007
  - ADR-003/C-002
  pros: Constraints such as the normalised name-plus-shop unique index and CHECK rules are written explicitly and reviewed
    as SQL; the spec cannot silently drift because code is derived from it; little hidden behaviour.
  cons: More SQL to write by hand; query-layer types must be kept in step with migrations.
  cost: No licence cost known; build effort not stated (A-008).
  reversibility: two-way
  risks: A hand-written migration can be wrong; mitigated by running all migrations on an empty real PostgreSQL in every integration
    run.
  constraints:
  - id: ADR-008/C-001
    statement: The schema changes only through ordered, forward-only migration files in the repository. The R-003 uniqueness
      is a unique index on normalised name and shop, and R-002 required values are NOT NULL or CHECK constraints.
    kind: data
    check: review
  - id: ADR-008/C-002
    statement: Migrations are applied by a release step before traffic moves to a new revision, never at container start by
      several instances at once, and each new migration works with the previous revision still running.
    kind: deployment
    check: review
  - id: ADR-008/C-003
    statement: IF-001 server types and validators are generated from the approved openapi.json; CI regenerates them and fails
      on a difference, and generates the implemented-interface report that the conformance check compares with the approved
      version.
    kind: interface
    check: review
  - id: ADR-008/C-004
    statement: Integration tests run every migration on an empty real PostgreSQL and check each IF-001 response against the
      spec.
    kind: technology
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: IF-001 changes start in the spec through a design PR, then regenerate code. DevOps owns the release step that
    runs migrations.
  cites:
  - ADR-003/C-002
  - ADR-001/C-002
  - S-ARCH-021
  - A-008
- key: b
  summary: 'Spec-first as in a, but with an ORM: the schema is defined in code models and migrations are generated from model
    changes and then reviewed.'
  satisfies:
  - REQ-003
  - REQ-007
  - ADR-003/C-002
  pros: Less hand-written SQL; models and migrations stay together.
  cons: Generated migrations can hide the exact constraint; normalised uniqueness (R-003) often needs a hand-written expression
    index anyway; the ORM adds a layer to learn and update.
  cost: No licence cost known; build effort not stated (A-008).
  reversibility: costly
  risks: ORM defaults can drift from the intended constraints; moving off the ORM later touches every query.
  constraints:
  - id: ADR-008/C-005
    statement: Generated migrations are reviewed before commit; the R-003 normalised unique index and R-002 required values
      are verified by an integration test against a real PostgreSQL.
    kind: data
    check: review
  - id: ADR-008/C-006
    statement: Migrations are applied by a release step before traffic moves, and each works with the previous revision still
      running.
    kind: deployment
    check: review
  - id: ADR-008/C-007
    statement: IF-001 server types and validators are generated from the approved openapi.json; CI fails on a difference.
    kind: interface
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: The ORM becomes a dependency of CMP-002 only (ADR-003/C-002 still holds).
  cites:
  - ADR-003/C-002
  - knowledge/rules/catalog/R-003.md
  - A-008
- key: c
  summary: 'Code-first: the backend declares routes and schemas in code, the OpenAPI document is generated from the code,
    committed, and CI diffs it against the approved openapi.json. SQL migrations as in a.'
  satisfies:
  - REQ-003
  - REQ-007
  - ADR-003/C-002
  pros: The route and schema definitions sit next to the handlers; the generated document is itself the implemented-interface
    report.
  cons: The approved spec no longer drives the code, so a spec-first review can be bypassed by editing code until the diff
    passes; a generated document may differ in description, unit or security text, which counts as breaking (S-ARCH-022).
  cost: No licence cost known; build effort not stated (A-008).
  reversibility: two-way
  risks: Spec and code are kept equal by a check after the fact, not by construction.
  constraints:
  - id: ADR-008/C-008
    statement: The OpenAPI document generated from code must equal the approved IF-001 version, including descriptions, units
      and security schemes; any difference fails CI.
    kind: interface
    check: review
  - id: ADR-008/C-009
    statement: The schema changes only through ordered, forward-only SQL migration files applied by a release step, with the
      R-003 normalised unique index and R-002 constraints in the database.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: Interface changes are made in code and in the spec together through a design PR.
  cites:
  - S-ARCH-021
  - S-ARCH-022
  - ADR-003/C-002
  - A-008
recommended:
  option: a
  reason: Spec-first matches S-ARCH-021 (the approved version precedes code), keeps the database constraints behind R-002
    and R-003 explicit and testable, and keeps ADR-003/C-002 unchanged. It is also the least coupled to the ADR-007 choice.
