context:
  text: 'REQ-006 needs dishes: a name and at least one line, each line a product id with grams or pieces (R-007). A change
    of products or amounts records a new dish and the old one stays unchanged (R-008). A dish keeps pointing at the old product
    when that product gets new nutrient values (R-009). Delete is soft, restore is allowed, names may repeat (R-010). Nothing
    for dishes exists yet: IF-001 1.2.0 covers products only. ADR-010 option a (accepted) solved the same shape for products
    with replaced_by and deleted_at on one table. ADR-011 option b versions piece_weight, so a product id has one fixed piece
    weight, which keeps line weights stable. Migrations are forward-only and must work with the previous revision running
    (ADR-008/C-001, C-002). Only CMP-002 reaches the database (ADR-003/C-002). Plans and the journal will read old and deleted
    dishes by id.'

options:
- key: a
  summary: Two new tables. dishes holds id, name, replaced_by (nullable, foreign key to dishes), deleted_at (nullable), created_at.
    dish_lines holds dish_id, position, product_id (foreign key to products), and exactly one of grams or pieces. A dish is
    selectable when replaced_by and deleted_at are both null. An edit of products or amounts inserts a new dish with new lines
    and sets replaced_by on the old one. No unique index on name.
  satisfies:
  - REQ-006
  - ADR-008/C-001
  - ADR-008/C-002
  - ADR-010
  pros: Same pattern as ADR-010, so one model for the developer and for later features. Only new tables, so no data rewrite
    and the previous revision keeps working. Real foreign keys give each line its exact product id (R-009). Lines are queryable
    by product id, for example to find dishes that use a product.
  cons: Selectability is a derived rule every dish query must apply. A dish version is a chain of rows, not a grouped entity.
    A dish read joins lines and products.
  cost: One migration and new store and handler code in CMP-002. Build effort not stated (A-008).
  reversibility: costly
  risks: A query that skips the selectable predicate would offer old or deleted dishes. A later UPDATE of a line would break
    the old-version guarantee. Mitigated by one shared predicate and integration tests against real PostgreSQL (ADR-008/C-004).
  constraints:
  - id: ADR-012/C-001
    statement: 'Migration 005 is forward-only and adds only new tables, so the previous revision keeps working. dishes: id
      text primary key, name text not null with a check that it is not blank, replaced_by text null references dishes(id)
      deferrable initially deferred, deleted_at timestamptz null, created_at timestamptz not null, and a check that replaced_by
      and deleted_at are not both set. dish_lines: dish_id text not null references dishes(id), position integer not null,
      product_id text not null references products(id), grams numeric null, pieces numeric null, primary key (dish_id, position),
      a check that exactly one of grams and pieces is set and that it is above 0, and an index on product_id. There is no
      unique index on dishes.name (R-010).'
    kind: data
    check: review
  - id: ADR-012/C-002
    statement: Dish ids are never changed or reused and dish rows are never physically deleted. dish_lines rows are written
      only when their dish row is inserted and are never updated or deleted. Only dishes.name, dishes.replaced_by and dishes.deleted_at
      change after insert.
    kind: data
    check: review
  - id: ADR-012/C-003
    statement: getDish returns a dish in any state. listDishes returns only selectable dishes unless state=deleted is asked
      for, and never returns replaced versions. One shared predicate in CMP-002 decides selectable, and every selection uses
      it.
    kind: interface
    check: review
  - id: ADR-012/C-004
    statement: A versioned edit inserts the new dish and its lines and sets replaced_by on the old dish in one transaction.
      The update of the old row is conditional on replaced_by and deleted_at being null, so an edit of a dish that was just
      replaced or deleted is refused with dish.not_selectable.
    kind: data
    check: review
  - id: ADR-012/C-005
    statement: A dish line stores the product id it was saved with and that id is never rewritten to a newer product version.
      Line weight is computed on read (grams, or pieces times the product's piece_weight) and is never stored. A log entry
      or plan that holds different amounts keeps its own lines outside the dishes tables and never writes to a dish. Other
      areas reach dishes only through IF-001, by id.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: IF-001 1.3.0 exposes replaced_by, deleted and selectable on Dish so plans and the journal can detect a replaced
    or deleted dish without reading tables. Plans and journal can keep a dish id and read it later in any state (AC-010, AC-011).
  cites:
  - ADR-010
  - R-008
  - R-009
  - R-010
  - ADR-011/C-002
  - A-008
- key: b
  summary: Split into a dish identity table that points to a current version, and a dish_versions table with a version id,
    name and lines. Soft delete is a flag on the identity row.
  satisfies:
  - REQ-006
  - ADR-008/C-001
  pros: Version history is a first-class group. Finding the current dish is a single pointer read.
  cons: A second id model next to ADR-010's. Past records must reference a version id, not the dish id, so two ids per dish.
    More tables and joins.
  cost: Larger schema and handler work than a. Build effort not stated (A-008).
  reversibility: costly
  risks: Two id models in one catalog invite mistakes in later features. No source asks for grouped history, so the structure
    is unproven (ADR-010 option b was rejected for the same reason).
  constraints:
  - id: ADR-012/C-006
    statement: Past records reference a dish version id, which is never changed or reused. Version and line rows are immutable.
      The migration is forward-only, adds only new tables and works with the previous revision running.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: Other areas must learn the identity and version split.
  cites:
  - ADR-010
  - ADR-008/C-002
  - A-008
- key: c
  summary: One dishes table with the same replaced_by and deleted_at columns, and the lines stored as a jsonb array on the
    dish row.
  satisfies:
  - REQ-006
  - ADR-008/C-002
  pros: One table, one write per dish, a dish is read as one row.
  cons: No foreign key from a line to products, so R-009 integrity rests on application code only. Dishes that use a product
    cannot be found with a plain query. Product values still need a join in code.
  cost: Smaller migration than a. Build effort not stated (A-008).
  reversibility: costly
  risks: A line could point at a product id that does not exist. Moving to real line rows later needs a data migration of
    every dish.
  constraints:
  - id: ADR-012/C-007
    statement: dishes.lines is jsonb not null and is written only on insert. The product ids inside it are checked against
      products by CMP-002 before insert. replaced_by, deleted_at and the other rules of ADR-012/C-002 to C-005 hold unchanged.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: Integrity of lines depends on code, not the database.
  cites:
  - R-009
  - ADR-003/C-002
  - A-008
recommended:
  option: a
  reason: It meets R-007 to R-010 with the same pattern ADR-010 already uses, adds only new tables (ADR-008/C-002), and gives
    each line a real foreign key to its exact product id (R-009). Options b and c add structure or lose integrity that no
    requirement needs.
