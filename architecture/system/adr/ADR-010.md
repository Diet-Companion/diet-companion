context:
  text: R-004 records a new product when nutrient values change and keeps the old one for past records. R-006 soft-deletes
    and allows restore. R-003 forbids two selectable products with the same name and shop, and says earlier versions and soft-deleted
    products are not selectable. The products table has no version or deleted state, and unique index products_name_shop_key
    (migration 001) covers every row, so AC-013 (nutrient edit is not a duplicate) and AC-016 (reuse a deleted name) cannot
    pass. The backend maps a unique violation on that index name to product.duplicate_name_shop. Migrations are forward-only
    and must work with the previous revision running (ADR-008/C-001, C-002). Only CMP-002 reaches the database (ADR-003/C-002).
    Later features (day plans, log entries, dishes, shopping plan) must keep reading old and deleted products by id.

options:
- key: a
  summary: Keep one products table. Add nullable replaced_by (the id of the newer version) and deleted_at. A product is selectable
    when both are null. The unique index is rebuilt as a partial index over selectable rows only.
  satisfies:
  - REQ-005
  - ADR-008/C-001
  - ADR-008/C-002
  pros: Smallest change. Existing rows stay selectable with no data rewrite. The old version keeps its id and row, so past
    records stay valid. The version chain is a plain column and the database enforces R-003 on selectable rows.
  cons: Selectability is a derived rule that every query must apply. Version history is a chain of rows, not a grouped entity.
  cost: One migration and changes to the store and handlers in CMP-002. Build effort not stated (A-008).
  reversibility: costly
  risks: A query that forgets the selectable filter would offer old or deleted products. Reversing later means a data migration.
    Mitigated by one shared selectable predicate and integration tests against real PostgreSQL (ADR-008/C-004).
  constraints:
  - id: ADR-010/C-001
    statement: Migration 004 is forward-only. It adds replaced_by (text, null, foreign key to products(id), deferrable initially
      deferred), deleted_at (timestamptz, null) and a CHECK that replaced_by and deleted_at are not both set. In one transaction
      it drops and recreates unique index products_name_shop_key with the same name and the same normalised expressions, restricted
      by WHERE replaced_by IS NULL AND deleted_at IS NULL. Existing rows get nulls, so they stay selectable. A product is
      selectable when both columns are null.
    kind: data
    check: review
  - id: ADR-010/C-002
    statement: Product ids are never changed or reused, and product rows are never physically deleted. The columns that ADR-011
      classes as nutrient values are written only when the row is inserted.
    kind: data
    check: review
  - id: ADR-010/C-003
    statement: getProduct returns a product in any state. listProducts returns only selectable products unless state=deleted
      is asked for, and never returns replaced versions. One shared predicate in CMP-002 decides selectable, and the duplicate
      check and every selection use it.
    kind: interface
    check: review
  - id: ADR-010/C-004
    statement: A versioned edit sets replaced_by on the old row and inserts the new row in one transaction. The update of
      the old row is conditional on replaced_by and deleted_at being null, so a concurrent edit of a product that was just
      replaced is refused with product.not_selectable. Other components and areas reach products only through IF-001, by id.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: IF-001 1.2.0 exposes replaced_by, deleted and selectable so later features can detect that a product was replaced
    or deleted without reading the table. The name products_name_shop_key is kept so the previous revision still maps duplicates
    correctly during a deploy.
  cites:
  - R-003
  - R-004
  - R-006
  - ADR-008/C-002
  - A-008
- key: b
  summary: Split into a product identity table and a product_versions table. Each version row has its own id and values. The
    identity row points to the current version, and soft delete is a flag on the identity row.
  satisfies:
  - REQ-005
  - ADR-008/C-001
  pros: The version history is a first-class group. A name-and-shop index on current versions can be simple.
  cons: Existing rows and all queries must be moved to the new tables. The old and new ids both need to resolve, which duplicates
    the id model. The deployed previous revision reads the old table, so the migration needs a compatibility view or a two-step
    rollout.
  cost: Larger migration and rewrite of the store and handlers. Build effort not stated (A-008).
  reversibility: one-way
  risks: Moving data while the previous revision runs is hard under ADR-008/C-002, and a mistake would corrupt ids that past
    records point to. No source needs grouped history, so the extra structure is unproven.
  constraints:
  - id: ADR-010/C-005
    statement: The migration to identity and version tables is forward-only, keeps every existing product id valid, and works
      with the previous revision running, for example by a view named products. Constraints ADR-010/C-002 to C-004 hold unchanged.
    kind: data
    check: review
  affects:
  - CMP-002
  - IF-001
  consequences: A larger one-time data move, and a model other areas must learn.
  cites:
  - ADR-008/C-001
  - ADR-008/C-002
  - R-004
  - A-008
recommended:
  option: a
  reason: It meets R-003, R-004 and R-006 with the smallest forward-only change, keeps every existing id and row valid, and
    works with the previous revision running (ADR-008/C-002). Option b adds structure that no requirement needs.
